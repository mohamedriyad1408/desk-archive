## 3) تصديقي على المصفوفة — مع تحرير إلزامي

أصدق ب1–ب16 وت1–ت10، وأضيف ب17 وب18، لكن أصحح الصياغات التالية قبل اعتبار المصفوفة مرجع الجلسة:

### ب3 — ليس «أربعة صناديق» بإطلاق

الصياغة الصحيحة من تفسير واو v1.1:

- `requirement_disposition`: خمس قيم حصرية: in-plan / owner-package / representation-blocker / deferred-with-reason / out-of-scope-with-reason.
- `discovery_routing_bin`: أربعة مسارات: plan / owner / representation / knowledge-gap.

خلط الجدولين يعيد التناقض الذي عالجناه.

### ب5 وب6 — أسماء profiles

لا L0/L1/L2 بعد إسقاط سلم L0–L5. تعتمد:

`intake-minimal | intake-standard | intake-external-critical`

وعمق الدليل مستقل عنها عبر claim/risk profile.

### ب8 — حد 50KB ليس Core

Core يقول `bounded active state` مع budget قابل للقياس؛ قيمة 50KB في Environment Profile بحسب نافذة السياق والأداة.

### ب10 — لا دورية

Core: status publication on material transition only. أي throttle/مهلة رقمية في Environment Profile. أقبل تحرير ن: لا heartbeat دوري؛ وإن وجدت بيئة تحتاج liveness probe فبروفايلها يثبت حاجتها ومعدلها ولا يدفع ضجيجًا معرفيًا.

### ب11 — لا «خمسة صفوف» حدًا عامًا

سجل الناسخ يغطي كل مصدر حاكم مهما كان عدده، بحقول id/version/hash/status/supersedes/absorbed-at. العدد نتيجة لا معيار.

### ب14 — اللغة Profile

Core يطلب authority language + operational language + clause mapping + conflict rule. العربية/الإنجليزية تعيين Language Profile لهذه الحزمة بأمر المالك.

### ب17 — العموم والأفقية (مقبول حاجبًا)

إغلاقه ليس حذف 65 token فقط، بل الفصل:

`Universal Core + Team Topology Profile + Execution Environment Profile + Project/Domain Profile + non-normative Rationale Ledger`.

وشروطه: صفر incident/provider/tool/path binding في Core؛ صفر fixed team cardinality غير مسبب؛ profile schema واختبارات compatibility؛ cold-start أربع بيئات؛ وتعميم واو v1.1 مع حفظ الأصل التاريخي غير معياري.

## 4) ب18 — أقبله حاجبًا، وأصحح آلية إغلاقه

اقتراح «اتحاد آخر 3 أحجام على الأقل» مفيد كمسكّن، لكنه **ليس invariant كافيًا**: فقد قديم يتجاوز النافذة يصير أساسًا صحيحًا كاذبًا مرة أخرى.

الحكم العام:

> كل مسار عاش تاريخيًا يظل live حتى tombstone مصرح به؛ لا يجوز أن يختفي لأن نافذة المقارنة انزلقت.

### عقد ب18

1. **Cumulative live-set manifest**: مجموعة المسارات الحية وبصماتها أو Merkle root، متسلسلة بإصدارة وparent.
2. **Explicit tombstones**: الحذف الوحيد المشروع يحمل path/id + authority + reason + timestamp/revision.
3. **Race reconciliation**: الختم يبدأ من base volume معلن، ويصالح كل volume ظهر بعده حتى remote head؛ لا يقفز إلى «آخر واحد» فقط.
4. **CAS/fast-forward gate**: لا دفع من شجرة لم تثبت نسبها إلى الرأس البعيد الحالي.
5. **Candidate diff report**: added/changed/missing/resurrected/tombstoned مطبوع قبل التشفير والدفع.
6. **Automatic recovery**: missing غير tombstoned يستعاد من آخر manifest/volume يحمله، ثم يفشل الختم ليجبر المراجعة بدل دفن الاستعادة صمتًا.
7. **Periodic full-history audit/compaction**: يثبت أن cumulative manifest يساوي اتحاد التاريخ ناقص tombstones.
8. **Acceptance kill:** ثلاث ختوم متسابقة تُسقط في كل منها ملفًا مختلفًا عمدًا؛ يجب أن ترفض الثلاثة، ثم حذف مصرح ينجح، ثم recovery drill يعيد ملفًا قديمًا تجاوز K volumes.

يمكن استخدام نافذة K لتحسين الأداء، لا بوصفها مصدر الحقيقة. مصدر الحقيقة cumulative manifest + tombstone chain.
