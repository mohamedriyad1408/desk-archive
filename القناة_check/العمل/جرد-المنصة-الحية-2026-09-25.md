## ٢ · الفحوص الآلية — كم وما تحرس وما الذي يعمل الآن

**العدّ المقيس:** ١٨٤ اختبار وحدة + ١٧ مواصفة e2e + **٤٠ سكربت تحقق** (`verify:*`) + ٤ مسارات CI (MJRH CI · Weekly Review · CI Self-Heal · docs-check ضمن CI).

**ما تحرس فعلًا (بوابات لا ديكور — كل واحدة تُسقط البناء):**
- **العزل بين المستأجرين:** `verify:isolation` + `verify:new-tenant` + اختبار سلوكي عابر للمستأجرين داخل المراجعة الأسبوعية.
- **الحقن والمحو:** `verify:append-only` (سجلات لا تُمحى) · `verify:no-destructive-paths` (لا مسار حذف مدمر) · حارس حذف الموثّق.
- **الرحلات:** `verify:journeys` + e2e مقيسة `verify:e2e-measured` (منع الاختبارات المتخطاة).
- **الصلاحيات:** `verify:permission-source` + إحصاء `census:permission-source` + أطلس وصول الشخصيات (`verify:access-atlas`).
- **العمارة:** `verify:architecture` + `verify:closure` + `verify:deps` + قياس الدين `measure:debt` + تعقيد `measure:complexity`.
- **الاتساق الوثائقي:** اختبار **«الوثائق تطابق الواقع»** يُسقط البناء عند أي ادعاء لم يعد صحيحًا (وُلد بعد اكتشاف ٤ ادعاءات خاطئة في الوثائق).
- **تغطية أخطاء القاعدة:** `verify:db-errors` (جدول رسائل لكل RPC) · `verify:rpc-coverage` · `verify:decision-log` · `verify:sovereign-engine` · `verify:period` · `verify:guards`.

**أيها يعمل الآن على البنية الحالية (مقيس من GitHub Actions على main):**
- ✅ **MJRH CI أخضر على main** (آخر تشغيل ٣١/٠٨ 17:51): typecheck + tests + e2e + build.
- ❌ **Weekly Security & Permission Review أحمر ٣ مرات متتالية** (٧/٩ · ١٤/٩ · ٢١/٠٩) — **السبب المقيس من سجل الفشل حرفيًا:** اختبار العزل السلوكي يُدخل عميلًا بهاتف ثابت `01000000001` فيصطدم بقيد الفريدية **العالمي** `customers_phone_key` (الهاتف فريد عبر كل المستأجرين لا داخل الواحد) — فالعُدّة معطوبة **والكشف تصميمي حقيقي معًا**: مستأجران لا يمكن أن يشاركا عميلًا بنفس الهاتف، وهذا يجب حسمه عند التعميم (قيد لكل مستأجر أم سجل عميل مشترك).
- ⚠️ CI Self-Heal موجود لكنه «متخطٍ» آخر دورتين.

## ٤ · قابلية التعميم — ما هو عدسة وما هو نواة

| خاص بالمغاسل → يُحوَّل إلى **عدسة** (يُحمَّل لكل قطاع) | عام → يُصبح **نواة** (يُفتح لأي نشاط) |
|---|---|
| جداول الكي الأربعة: `ironing_rates · ironing_daily_payouts · ironing_daily_rosters · ironing_order_allocations` | `tenants` + عزل RLS + بذرة مستأجر جديد |
| مفردات خط الغسيل في ٧٥ ملفًا (شاشات وقيود QC للكي/الغسيل: كي=1، غسيل/كلا=2) | جسم الطلب: `orders · order_items · order_status_history` + آلة الحالة `advance_order` |
| شاشة أجر الكي `staff/ironing-payroll` | `branches · zones` والفروع بمستويي التجميع |
| خدمات `service_items` بمصطلحات غسيل | سجل الأحداث `operation_events/event_log` والقياس عليه |
| تسلسل المحطات بمصطلحات مغاسل (استقبال/فرز/كي/تعليب) — **والبنية تحته عامة بفضل ADR-149** | الخزنة والقيود: `cash_* · journal_* · chart_accounts` |
| عتبات QC على مستوى الوحدة بمنطق غسيل | الصلاحيات بمصنّفيها + بوابة مصدر الصلاحية |
| | البوابة العامة والبووابات الأربع (`$slug · join · track · customer-portal`) |
| | التوصيل والمناديب والتسويات والخريطة الحية |
| | CRM · المخزون · الفواتير · التنبيهات · مركز التقارير |
| | الإدارة: مستأجرون · رسوم منصة · فوترة · تدقيق |

**الحاصل المقيس:** القطاع يسكن في **٤ جداول + ٧٥ ملفًا + شاشة أجر** — أما الهيكل الناقل (طلب · محطات قابلة للتهيئة · خزنة · قيود · فروع · صلاحيات · بوابة عامة · عزل) **عام كله**. النسبة: أقل من ١٠٪ من الشجرة تحمل هوية القطاع.

### ب · البناء من الصفر حتى نفس النقطة

الحجم الواجب إنتاجه: ١١٣ جدولًا · ٣٥٦ دالة · ٣٠٩ سياسات · ١٠٠ شاشة · ٨٢ ألف سطر TS · ٥١ ألف سطر SQL · ١٨٤ اختبار وحدة · ١٧ e2e · ٤٠ بوابة تحقق — **بشرط نفس مستوى الصدق المقيس** (بوابات تسقط البناء عند ادعاء كاذب، لا مجرد وظائف تعمل).

| المسار | الساعات |
|---|---|
| الوظائف فقط (بلا بوابات القياس والصدق) | ١٬٢٠٠–١٬٦٠٠ ساعة (٧–١٠ أشهر منفذًا واحدًا) |
| بنفس مستوى البوابات والقياس الموجود في MJRH | **٢٬٠٠٠–٣٬٠٠٠ ساعة (سنة–سنة ونصف)** — لأن مستوى القياس الحالي ثمرة عشرات جولات النقض والإصلاح الموثقة في ١٠٩ قرارات |

**السند الخارجي (بحث):** قواعد الصناعة على تطبيقات بحجم مشابه: إعادة البناء تساوي **٣–٥ أضعاف** كلفة التهييب/التعميم وتستغرق ١٢–٢٤ شهرًا مقابل ٣–٦ أشهر [1](https://www.qservicesit.com/legacy-app-modernization-rewrite-refactor) · سيناريو عمل محسوب: تهييب ١٢٠ يوم-مطور مقابل إعادة بناء ٣٢٠ يوم-مطور (≈٢٫٧×) [3](https://mecanik.dev/en/posts/legacy-software-modernisation-rewrite-vs-refactor/) · **ومعايير الميل كلها عندنا تشير للتعميم لا لإعادة البناء**: تغطية اختبار قائمة (١٨٤+١٧) · مخطط سليم · حزمة حديثة مدعومة · توثيق حي — وهي بالضبط شروط «هيّب لا تُعِد البناء» في مصفوفة القرار [3](https://mecanik.dev/en/posts/legacy-software-modernisation-rewrite-vs-refactor) · وإعادة البناء لا تُبرر إلا بكود عتيق أو دين غير قابل للسداد [2](https://horizon.dev/blog/rebuild-vs-refactor-legacy-software/) — وMJRH نقيض ذلك (نشط حتى ٣١/٠٨).

> **خلاصة القياس:** التعميم ≈ **١٣٦–١٨٦ ساعة** مقابل إعادة البناء ≈ **٢٬٠٠٠–٣٬٠٠٠ ساعة** لنقطة أضعف قياسًا — أي أن قرار «من الصفر» لو أُريد فعله فسببه عقيدة المالك لا اقتصاد الهندسة، وهذا حقه، والجرد يقدم الرقمين أمينًا.
